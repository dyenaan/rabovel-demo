## Demo promise and boundaries

An approved **demo issuer** defines a simulated Nigerian equity. Rabovel creates its zero-supply Token-2022 mint, configures account eligibility, and separately issues backed demo inventory to an eligible **broker wallet**. An approved investor links a Solana wallet, receives on-chain account activation, buys or sells the equity against a payment token in one atomic transaction, and sees confirmed balances and a receipt.

The flagship instrument is `RABO-NG-TELCO`: zero decimals, one token per simulated beneficial entitlement to one share, with a proposed authorized supply of 1,000,000 and first issuance of 100,000. These numbers are demo configuration, not a Token-2022 supply cap. Display **“Prototype / simulated asset / not an offering / not SEC-approved”** wherever the asset is presented. Issuer onboarding in the current UI is mock KYB, not real organization verification or authorization from a telecom company.

Payment assets are separate mints. Start with **demo CNGN**, then add **demo USDC** and **demo CADC** as supported payment choices. A mint created by Rabovel must be labelled a demo representation, never official cNGN, USDC or CADC. Use an official token only after verifying its mint address, network, token program, decimals and usable test supply. The broker must explicitly accept and hold an account for each payment mint. A quote in CADC or USDC settles in that chosen token; it does not imply an FX swap into CNGN. Actual FX conversion is a later product decision.

The initial buy is a **broker-to-investor inventory sale**. The initial sell is an **investor-to-broker sale** at a broker bid. They demonstrate two-way trading without claiming an order book or peer matching engine. Both sides must authorize spending their own token accounts. The API cannot spend an investor's self-custodied tokens merely because a worker received an event.

## Shared rules for every chain-facing slice

- Keep Admin, issuer, broker and investor signing powers distinct. Resolve privileged signers from trusted deployment configuration; never accept their key paths or authority labels from an HTTP request or event.
- Save a stable operation ID, intended accounts/amounts and signed transaction or signature before broadcast. On timeout, reconcile the known signature and accounts before considering another submission. Replaying a Kafka event must not repeat `MintTo` or DvP.
- Keep KYC/KYB documents and identities off-chain. Public wallet membership and token balances are not proof of legal ownership or real backing.
- Token ACL and ABL Gate govern **account activation**. The selected transfer hook is inactive and does not enforce settlement-only transfers. Do not claim every later transfer is checked by the Gate. A stronger transfer rule requires a separately designed and tested hook/program.
- For DvP, put payment and equity transfers in the **same signed Solana transaction**. Backend quote approval and required signatures govern the first demo. A custom on-chain order/escrow program is a later decision if asynchronous matching, enforced quote terms or settlement-only transfers are required.
- Default tests use mock signers, transport and event adapters. Add an opt-in local-validator check for chain instructions, then record a Devnet run. A passing mock test is not on-chain evidence.

## Next implementation handoff: slice 3

**Outcome:** An issuer with the current approved demo organization creates and edits an asset draft, then selects **Approve draft**. The demo records the decision immediately and shows the asset as `approved_for_setup`, with no mint, no inventory and no public trading listing.

**Scope:** Use the existing FE issuer layout and auth client for asset list/create/edit and an explicit issuer-owned demo approval action. No separate platform review screen or platform user is part of this demo. Keep asset ID independent from ticker. Use checked integer units for supply. Store the trusted issuer mapping and simulated disclosure/representation details. The request may select an approved demo payment-currency code; it may not select an Admin key, issuer key path or mint address.

**Lifecycle:** `draft → approved_for_setup` for the demo. The owning approved issuer may create and edit only while in `draft`, then select **Approve draft**. The transition is idempotent and stands in for external review; it is a mocked business decision, not chain confirmation.

**Acceptance:** Create one `RABO-NG-TELCO` draft (zero decimals, 1:1 simulated representation, 1,000,000 authorized units and CNGN settlement), edit it, and approve it from the issuer dashboard. Reject malformed values, duplicate instrument identity and cross-issuer access. Refresh to see persisted state. Verify the asset remains absent from the investor tradable catalog until slices 5–6 confirm setup and inventory. No validator is needed for this slice.

**Demo decision:** There is no platform approver role or separate review UI. The issuer-facing **Approve draft** control mocks that interaction and advances only `draft` assets to `approved_for_setup`. Keep the sandbox disclosure mandatory.

**Implementation evidence (2026-09-24):** Asset create/list/detail/edit and approval endpoints require an approved owning issuer. Approval publishes backend-generated metadata to Supabase Storage, persists its public URI, then performs a replay-safe `draft → approved_for_setup` transition. Publishing failure leaves the asset in draft. Approval locks subsequent edits and leaves mint address absent and issued units at zero. The canonical uniqueness key is issuer + market + ticker + share class; instrument code is independently unique per issuer. Authorized units are checked integers transported as strings. Domain and API tests cover validation, creation, editing, persistence/listing, duplicate rejection, approval and edit rejection after approval.

**Metadata hosting:** The issuer edits structured metadata and sees a generated JSON preview; arbitrary JSON upload is not supported. The backend publishes approved metadata to the public Supabase Storage `metadata` bucket at `assets/{asset_id}/metadata.json`. Editable drafts support PNG/JPEG/WebP image uploads up to 5 MB directly from the browser using a short-lived backend-issued signed URL under `assets/{asset_id}/images/`; the backend verifies and persists the public image URL.
